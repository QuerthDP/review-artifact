# Review page workflow

Shared by both skills: `/review-artifact` (the local app, answered by a background subagent that follows `local/agent.md`) and `/review-artifact-remote` (the claude.ai Artifact, answered by a cloud session that follows `cloud/prompt.md`). Each of those files says how it differs from this one.

Argument: a PR URL or `owner/repo#N` (or `N` in the current repo). The page is the review workspace: the user reads commits, asks Claude questions in place, asks Claude for changes, approves/rejects/revises Claude's comments, replies to other reviewers, and only what they **queue** lands in their pending GitHub review.

Files at the repository root `$R` (the directory holding `app/`; `~/.claude/skills/review-artifact` when installed as the README says): `app/` (the page as a static web app: `index.html`, `app.js`, and `loader.js` for the local server), `local/server.py` (the local app), `local/store.py` (Claude's access to its store), `scripts/mkdiff.py`, `scripts/ghthreads.py`, `scripts/build.py`, `scripts/seeds.py`, `scripts/ghsync.py`. Work in the session scratchpad (`$S` below), never in the repo. Run the session from a local clone of the PR's repo (the scripts use `git`). The scripts talk to GitHub over REST only (`gh api`), since GraphQL is blocked in cloud sessions.

## 1. Build (the claude.ai Artifact, for cloud sessions)

1. Fetch the PR over REST: `gh api repos/<repo>/pulls/<N> --jq '{number,title,author:.user.login,head:.head.sha,base:.base.ref}'` (`gh pr view` uses GraphQL). Fetch the head locally (`git fetch <remote> pull/<N>/head:pr-<N>`); base = merge-base with the base branch.
2. `python3 -I $R/scripts/mkdiff.py <repo_dir> <base> pr-<N> $S/diff.json`
3. `GH_LOGIN=<your login> python3 -I $R/scripts/ghthreads.py <repo_dir> <owner/repo> <N> $S/diff.json $S/gh.json` — other reviewers' review threads (anchored with `git blame` to the PR commit that last changed their line, each with `rootCommentId`, the numeric id of its first comment, which replies go to) and the PR conversation. `GH_LOGIN` is optional locally; set it where the user endpoint is unreachable. REST has no resolved state: one GraphQL read fills it in where GraphQL works, otherwise threads show neither "open" nor "resolved".
4. `$S/meta.json`: `{"repo": "<owner/repo>", "pr": <N>, "pr_title": "...", "author": "<PR author login>", "mine": <PR author == gh api user>, "session": "<this session's claude.ai/code url, if it has one>", "collapsed": ["Cargo.lock", ...]}` (lockfiles/generated files start collapsed). The page shows a Session button opening `session` when set. The page is titled `[<owner/repo>#<N>] <PR title> (by <author>)`; build.py derives it.
5. `python3 -I $R/scripts/build.py $R/app $S/diff.json $S/meta.json $S/pr<N>-review.html $S/gh.json`
6. Syntax-check: `node -e` with `new Function` over each `<script>` body.
7. Publish with the Artifact tool, `capabilities: {"db": {}, "user": {}, "comments": {}, "mcp": {"servers": [{"server": "<GitHub connector tool prefix, e.g. claude_ai_Github_CoPilot>", "tools": ["pull_request_review_write", "pull_request_read", "add_comment_to_pending_review", "add_reply_to_pull_request_comment", "add_issue_comment"]}]}}`; the page calls the connector by its display name (`GH_SERVER` in the template; the publish result names it), icon `code`. Republish the same file path for every later change (same URL). Rerun steps 3 and 5 to refresh reviewer threads.

## 2. Seed Claude's review

Review commit by commit (correctness first; verify claims by running code where possible). Write findings to `$S/findings.json` — `[{"commit": "<short>", "path": "<file>"|null, "snippet": "<exact text on the line>"|null, "side": "RIGHT", "body": "..."}]` (path null = commit-level; snippet null = file-level). Bodies: **at most two short sentences, about 30 words**: the problem in plain words, then one concrete fix. Cut background the reader can see in the diff, how you verified it, hedging ("might", "consider whether"), alternatives lists and restating the code. `Nit:` for style only. No headings; never cite line numbers (the comment sits on its line; name the code instead). Before seeding, reread each body and cut every word that does not change its meaning. Revisions, replies and suggestion texts keep these rules.

`python3 -I $R/scripts/seeds.py $S/diff.json $S/findings.json $S/writes.json`, then one `ArtifactData` `batch` with those writes. Never hardcode comments into the HTML.

On the user's own PR (`mine`) Claude never seeds comments meant for GitHub: every finding is a proposed change the user accepts or declines. Give each line finding `old` (the exact RIGHT-side lines, starting at the one holding `snippet`) and `new` (the fix; `[]` deletes), and each commit-level one `op: "drop"` or `op: "reword"` with the full new `message`; a finding with no concrete fix is left out. Run `seeds.py` with `--mine`: it writes `changes/claude_chg_<n>` docs (`status: proposed`, `reason` = the body).

Also import the user's existing pending GitHub review comments (if any: the PENDING review in `gh api repos/<repo>/pulls/<N>/reviews`, its comments from `.../reviews/<id>/comments`) as docs with `author: "user", source: "github", status: "queued", githubCommentId`, so the page shows them as "in your GitHub draft". Every sync after that imports new ones the same way (doc id `gh_<comment id>`, a reply placed under its reviewer thread, a line comment on the commit that introduced the line) and drops the doc of one deleted from the draft on GitHub. Such comments (like any made in GitHub's UI) lock the draft: later page comments are added at submit instead (§5); say so to the user.

## 3. Data model (db collections)

- `comments/<id>`: `commit, path, line, startLine (first line of a multi-line comment, else null), side (LEFT|RIGHT), body, author (claude|user), status (proposed|queued|rejected|revise|withdrawn|posted), replyTo (review thread node id, for replies to other reviewers), humanReviewed, discussion[{role,text,at}], discussionHidden, note, prevStatus, editedByUser, revisedAt, inDraft, githubCommentId, githubPath, syncPending, shellThreadId, source, replyToCommentId (rootCommentId of the replied thread), deleted (tombstone: deleted on the page while on GitHub; hidden, removed by the next sync)`. Written by ghsync only: `githubAnchor` (the head line(s) the draft comment was made on), `githubBody` (the text last written to GitHub, to tell edits made there), `deferred` (why the comment waits for the submit: `reply|file-level|commit-level|outside-diff|draft-locked|rejected-by-github|restore-failed|edited`), `githubPlan` (ready-to-post anchor and body for the submit), `githubQuote`, `githubConflict` (edited on GitHub, so the page version was not pushed), `githubError`, `deferredError` (a submit-time post failed; the doc stays queued). `githubThreadId` is no longer set.
- `threads/<id>`: in-page conversations with Claude — `kind (question|modify|feedback), commit, path, line, startLine (multi-line requests cover startLine..line), side (LEFT = asked about the commit's old line, RIGHT = its new line), onChange, newStart, newEnd, newLine (asked on the new lines of accepted change onChange, indexes newStart..newEnd into its `new`), about (id of the comment or reviewer thread the conversation was started on with i, drawn inside it; the question names its text), status (asked|answered), dismissed (viewer hid an answered one; restorable from the queue), messages[{role,text,at}], shellThreadId`.
- `changes/<id>`: proposed code changes, kept apart from `comments` (the GitHub sync reconciles every comment doc) — `commit, path, startLine (null for one line), line, side (RIGHT), old [lines as they are now], new [replacement lines; empty deletes], op (only on a whole-commit change, which has no path: `drop` or `reword`), message (the full new message for `reword`), oldMessage, reason (1–2 sentences), threadId, status (proposed|accepting|accepted|declined|failed|stale|landed), branch, newCommit, commitUrl, compareUrl, commentId (others' PRs: the queued suggestion comment), error, at, decidedAt, discussion[{role,text,at}], note, noteAt (set while a change revision request waits)`. The page shows each as a card with Accept / Ask Claude to revise / Decline at its lines (the card shows only the lines that differ between `old` and `new`, with two lines of context and the unchanged runs folded, so `old`/`new` may span a whole block) and, once `accepted`, overlays the new lines on the diff in amber; a whole-commit change shows its card in the commit-level section and, once accepted, strikes the dropped commit's title or shows the new message under it; `landed` hides it.
- Reviewer threads are not in the db: they are snapshotted into the page from `gh.json` at build time.

Claude's comments start **proposed**. Nothing reaches GitHub until the user clicks **Queue → GitHub draft** (or writes their own comment/reply, which is queued) — never queue on their behalf, never bulk-queue.

## 4. Respond to the page (automatic — the page pings this session)

The page sends a shell comment via `sendToClaude` for every action that needs Claude; it arrives as an artifact comment notification. The text prefix says what to do:

**Models.** Work that needs judgement runs on Opus; everything else runs on a smaller model.
- Opus: seeding the review (§2), `[page question]`, `[revision request]`, `[change revision request]`, `[modify request]`, and a `[feedback request]` that asks for a fix to the tool. If you are not Opus yourself, spawn one `Agent` with `model: "opus"` per request: give it the request line, the doc it is about, the repo dir, the state paths, how to reach the store, and the rules of this workflow for that request; it does the request end to end (writes the answer, comment or change docs itself) and returns one line. Keep answering other requests meanwhile and never touch a doc it is working on. `[review request]` keeps its own model choice below.
- Smaller model: everything mechanical, which needs no spawn when you run on one: marking changes `landed` or `stale`, relaying server refusals and failures, `[github sync]` runs, filing a feedback issue with no fix, handover notes. When you are Opus and such a job is long (a full `ghsync` reconcile, many docs to mark), hand it to an `Agent` with `model: "haiku"`.

- **New PR head, before anything else:** on every wake, and right after this session pushes to the PR, compare `gh api repos/<repo>/pulls/<N> --jq .head.sha` with `head` in `$S/ghsync.json`. If they differ, rebuild the page for the new head without being asked: fetch `pull/<N>/head` again, take the base as the merge-base with the base branch again (a rebase moves it), rerun steps 2, 3 and 5, update `head` in `$S/ghsync.json`, and republish to the same file path (same URL) without `capabilities`. Keep the database as it is: the page maps docs on rewritten commits to the new series. After the rebuild, mark every `accepted` change doc whose `new` lines are now in the new head's file `landed` (a whole-commit change: when the head has no commit with the dropped commit's subject, or has one with the new message), and an `accepted` or `accepting` one whose `old` lines are gone without its `new` ones arriving `stale`. Then handle the request that woke you, against the new head.

- The page shows only `threads/<id>`: replying in or resolving the shell comment thread (including the automatic reply) never answers the viewer. Every `[page question|modify request|feedback request <id>]` is done only once `threads/<id>` has the Claude message and `status: "answered"`; write it before resolving the shell thread.
- Every Claude message on the page (answers, follow-ups, feedback replies, revision notes) is really concise: one to three short sentences, the answer first, no preamble, recap or option lists unless asked. Point to `file:line` instead of quoting code.
- `[page question <threadId>] ...` → answer in `threads/<id>`: append `{role:"claude", text, at}` to `messages`, set `status: "answered"`. Concise. If the question asks for a review comment ("make a comment about it"), also create a Claude comment doc at the thread's anchor (`author: "claude", status: "proposed"`), set the thread's `commentId` to it (the conversation then links to the comment), and say so in the answer. A thread with `draft: "reply"` (the "Ask Claude to draft a reply" button or `a` on a reviewer thread or PR conversation comment; the user's note, if any, says what the reply should say) asks for exactly that: create a proposed Claude comment doc replying there, with `replyTo` = the thread's `about` (a reviewer thread id) and `replyToCommentId` = that thread's `rootCommentId` from `$S/gh.json`, plus its `commit`/`path`/`line`/`side`; or, when the thread has `replyToConv`, with `replyToConv` and `convAuthor` copied from it and `commit` = the first commit (`replyToConv` is the PR URL for a reply to the PR description). Set the thread's `commentId` and answer in one line. If it asks Claude to change code ("go ahead with the change", "fix it"), handle it like a `[modify request]`: write change docs and set the thread's `changeId`, never commit or rewrite a comment into a suggestion on your own.
- `[revision request <commentId>] <note>` → rewrite `comments/<id>.body`, append `{role:"claude", text: "<one line: what changed / answer>", at}` to `discussion` (the page already appended the user's note), set `status` back to `prevStatus` (or `proposed`), set `revisedAt`, delete `note`/`noteAt`/`prevStatus`. If it was in the draft, run ghsync to update GitHub. If the note is a question ("do these really need…?"), answer it in `discussion` and revise accordingly.
  If the conversation shows the comment no longer holds (the concern is wrong, moot or not worth raising), withdraw it instead of rewriting: keep `body`, set `status: withdrawn` and append the one-line reason to `discussion`. The page shows it struck through with a Restore button; a withdrawn comment that was `inDraft` leaves the GitHub draft on the next sync.
- A question or modify request whose thread has `onChange` was asked on lines an accepted change wrote; they exist only on the review branch. `newStart`..`newEnd` are the 0-based indexes of exactly those lines in that change's `new` (a range when they differ) and `newLine` quotes them; answer and change exactly those lines. Read it there, and for a modify request write the new change doc against the PR line the accepted change sits on (its `path`, `startLine`/`line`), with `old` = that change's `new` lines as they are on the review branch now; a change accepted later over the same lines replaces the earlier one on the page. The page shows such a proposed card under the line it edits (found by diffing its `old`, which equals the accepted change's `new`, against its `new`; or set `onChange` and `newEnd` on the change doc to place it).
- `[change revision request <changeId>] <note>` (the viewer's note on a proposed change card) → rewrite `old`/`new`/`reason` of `changes/<id>` as the note asks (`old` still copied exactly from the RIGHT side of that commit; for a whole-commit change, `op`/`message`), append `{role:"claude", text: "<one line: what changed / answer>", at}` to its `discussion` (the page already appended the note), delete `note`/`noteAt`, keep `status: "proposed"`. If the note is a question, answer it in `discussion` and revise only if needed.
- `[modify request <threadId>] <what to change>` (thread `kind: "modify"`, anchored to a line): don't touch the code yet. Write a change doc (one per place when the change touches several places, e.g. a declaration, its definition and its tests; to drop a commit or change its message, one whole-commit change with no path, `op: "drop"` or `op: "reword"` and the full new `message`; the thread's `changeId` names the first) `changes/<id>` at the thread's lines (`old` copied exactly from the RIGHT side of that commit, `new` with exact indentation, a short `reason`, `status: "proposed"`, `threadId`), set the thread's `changeId`, and answer in the thread with one line pointing to the card. The user decides on the card.
- `[accept change <id>]` (the user clicked Accept). Accepting is instant on the page: the doc is already `accepted` and drawn on the diff, with `applied: false` on the user's PR; the user does not wait for you. Handle accepts one at a time, in the order they came: each rewrites the series the next one applies to. When done, set `applied: true` with the fields below; on failure set `status: failed`. (An older doc may still say `accepting`; treat it the same.)
  - **PR authored by the user** (`mine`): before touching anything, keep the current version: `git branch review/pr-<N>-v<k> <current head>` (next free k). Commit as the user, never as Claude: unless `git config user.email` already gives the user's own address, set `user.name` and `user.email` in that checkout's config to the committer of the PR head commit (`git log -1 --format='%cn%n%ce' <head>`), so rewritten commits keep the user as committer (a committer outside the PR's organization fails its checks). Apply `old` → `new` in the commit that introduced the lines: commit it with `git commit --fixup=<that sha>` and fold it with `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash --empty=drop <base>` (a commit the change empties is dropped); resolve conflicts carefully. A whole-commit change instead edits the todo list: `drop` turns that commit's `pick` into `drop`, `reword` rewrites its message (`GIT_SEQUENCE_EDITOR="sed -i 's/^pick <short sha>/edit <short sha>/'"`, then `git commit --amend -F <file>` and `git rebase --continue`). Never push (the cloud session pushes a review branch to the user's fork; its prompt says how). Do not rebuild the page from the new commits: the page keeps showing the PR and overlays the change. Set `applied: true`, `newCommit` (the rewritten commit), `branch`. If `old` no longer matches or the rebase fails, abort it, restore the kept branch and set `status: failed` with a one-line `error`. This Accept click is the commit authorization; it covers only that change.
  - **Someone else's PR:** the page itself queues the suggestion as a Claude comment doc `sugg_<id>` and sends a `[github sync]`; handle that sync as usual. Only if a change doc is accepted without `commentId` (an older page): don't touch the code. For a whole-commit change, create a queued commit-level Claude comment doc (no path) whose body is the `reason` plus the proposed message in a quote, or the request to drop the commit; otherwise create a Claude comment doc on those lines (`author: "claude", status: "queued"`, `syncPending: true`) whose body is the `reason` plus a GitHub suggestion block (three backticks + `suggestion`, the `new` lines, closing backticks), run the sync as for a `[github sync]` request, then set the change doc's `status: accepted` and `commentId`.
- A change doc set `declined` by the page needs nothing from Claude.
- `[push review branch <id>] <branch> (<change ids>)` → the user clicked "Push to the PR" twice on their own PR: the review branch is approved. Force-push it with lease onto the PR's head branch, and only when that branch lives in the user's own fork (`head.repo.full_name` is `<login>/<name>`). Never push to the upstream repo or any repo of its org (e.g. `scylladb/*`), whatever the PR says; if the head branch is not on the user's fork, refuse and say so. Then rebuild the page for the new head as for any push; the accepted changes become `landed`.
- `[feedback request <threadId>] <feedback>` (thread `kind: "feedback"`, shown only in the panel by the Feedback button, never in the diff) → feedback about this tool, not the PR. Write a concise issue (title + what happened / what's expected). Never name the reviewed PR, repo, author or commit in it: the tool's repo is public and file it with `gh api repos/QuerthDP/review-artifact/issues -f title=<title> -F body=@<file>` (`gh issue create` uses GraphQL), ending the body with the `claude` badge from the badge config (§5; no `ai-assisted` label on issues). Answer in the thread with one line and the issue link. If the feedback asks for a fix and you can push to the skill repo, fix the tool itself: make the change in `$R`, commit it (short message in plain words) and push it to `main`, republish the page if the fix touches it, and name the commit in the answer. A fix made only in the scratch copy of the page is lost.
- `[post conversation replies <id>] <comment ids>` → the user clicked "Post queued conversation replies" (a deliberate, two-click action). For each listed doc still `queued` with `replyToConv`: `gh api repos/<repo>/issues/<N>/comments -F body=@<file>` with `In reply to [<convAuthor>](<replyToConv>):` + blank line + the body (the user's own text: no badge). Then update the doc: `status: "posted"`, `githubUrl`, delete `syncPending`.
- Submitting normally needs no Claude: the page calls the viewer's GitHub connector itself (`pull_request_read` for the draft's body, `add_comment_to_pending_review` for held-back comments, `submit_pending`, `add_reply_to_pull_request_comment` for replies, `add_issue_comment` for queued conversation replies), shows its progress, and marks each doc posted once its call succeeded. It falls back to Claude only when docs are still syncing, the connector is missing, or the call fails:
- `[submit review <id>] event=<COMMENT|APPROVE|REQUEST_CHANGES> postConversationReplies=<yes|no>` + optional summary on the next lines → the user clicked "Submit review" twice (`u` opens the panel), so submitting is authorized. If `postConversationReplies=yes`, post queued `replyToConv` docs as above. Write the summary to a file (the user's text: no badge), list the docs afresh as for a sync, run `python3 -I $R/scripts/ghsync.py $S/ghsync.json $S/docs --submit <event> --body-file <file>` and apply its batch. It reconciles first, submits keeping the draft's own body ahead of the summary, then posts every deferred comment (replies into their threads, the rest as single comments); one that fails stays queued with `deferredError`. Never mark a doc posted yourself unless the script did. Never submit without this request. Leftover deferred comments after a submit (the page shows a "GitHub error" pill) are posted by the same command with `--submit COMMENT` and no body file, once the user asks.
- `[review request <id>] scope=pr ...` → the user clicked "Ask Claude to review" twice. Spawn one `Agent` with `model: "fable"`; if that call fails because the model is unavailable, spawn it again with `model: "opus"` and `effort: "high"` (the user's explicit choice). Give it the repo, PR number, commit list and `$S/diff.json`, the §2 review rules (on the user's own PR: every finding with its `old`/`new` fix, or a drop/reword), and the bodies of the comments and changes already on the page so it skips duplicates; it returns only the findings JSON. Seed them as in §2 (`seeds.py`, with `--mine` on the user's own PR, one `batch`), then resolve the shell thread. Say in the chat which model ran.
- `[github sync <commentId>] ...` → one run reconciles **every** comment doc with the draft (adds and edits rebuild the draft, so all draft comment ids change), so pings that arrive together need one run: `rm -rf $S/docs` (a list only adds files, and a stale one would be synced again), `ArtifactData list comments` with `out_dir: $S/docs` and `query: {limit: 1000}` (a doc missing from the list reads as a comment made on GitHub), then `python3 -I $R/scripts/ghsync.py $S/ghsync.json $S/docs`, and apply the printed array as **one** `batch`, giving every entry `if_version` from the list result (the saved files carry no version). Resolve every shell thread the run covered. On "draft changed on GitHub during sync", rerun. If the script prints RESTORE FAILED, tell the user and name the snapshot file it printed (the old draft's comments are in it).
Then resolve the shell comment thread (`ArtifactComments resolve`). An auto-reply from the harness ("On it…") does NOT mean the work was done — always do the work. When the user asks "are you responding?", query **all** pending state: comments with `status: revise`, changes with a `note`, threads with `status: asked`, docs with `syncPending`, and open shell threads.

`$S/ghsync.json`: `{"repo_dir": "...", "repo": "<owner/name>", "pr": <number>, "head": "<PR head sha>", "diff": "$S/diff.json", "gh": "$S/gh.json", "snapdir": "$S/ghsync-snapshots"}` (optional `"login"` saves one API call; set it where the user endpoint is unreachable). The script finds the user's pending review itself on every run and creates one only when a comment must go in; the draft stays private until the user submits it. It snapshots the draft before every change; keep the snapshots for the session. Never submit the review outside a `[submit review]` request.

## 5. GitHub rules

- Badges are a per-user choice, read from `~/.config/review-artifact/badges.json` (`{"claude": "<html>", "human": "<html>"}`); without that file nothing gets a badge. When it exists, everything Claude writes to GitHub through this skill ends (after a blank line) with the `claude` badge: review comments and suggestions (ghsync adds it), feedback issues and the comments closing them. The `human` badge goes next to it only on comments with `humanReviewed` true (the user clicked "Add Reviewed by Human"). Copy the HTML from the file, never retype it. No prefixes like `**[Claude]**`. No Claude session links anywhere. The user's own comments and replies get no badge.
- Line comments are mapped from the commit's line to the PR head. REST can create a draft with line comments but cannot add to one, edit a draft comment, or put a reply or file-level comment into it, so: deleting a comment from the draft is a single delete; adding or editing one rebuilds the draft (snapshot, delete, recreate, verify, restore on failure), and only when every comment in it was made by the sync and is unchanged on GitHub. Comments made or edited in GitHub's UI are never deleted or rewritten: they lock the draft until it is submitted.
- What cannot go into the draft now waits as `deferred` and is added at submit: replies (posted into their threads right after the submit), file-level comments, commit-level ones (a file comment on the commit's most-changed file, quoting the subject as `> subject`), lines outside the PR diff (a file comment linking the line), and anything queued while the draft is locked. The page adds them through the viewer's connector before submitting; nothing is marked posted until its own call succeeds.
- PR conversation (issue comments, review bodies) can't be part of a pending review, so replies to it (`replyToConv`, `convAuthor`) stay queued on the page and are never synced to the draft. They are posted only when the user clicks "Post queued conversation replies".

## 6. Page features (keep when editing the page code in `app/`)

Commit stepper (its dots show, per commit, proposed and queued comments, changes to decide (amber square; decided ones are not shown), conversations with Claude (teal; outlined while unanswered) and open reviewer threads (blue), counted in its tooltip); a "PR · overview" tab before the first commit (`[`/`]` and the stepper reach it; `#overview`) with the PR description and, under it, each main-thread conversation item (review summaries and non-inline comments) as its own thread card with a queued reply (in the local app the server reloads this GitHub data, and open tabs, when the PR changes on GitHub without a new head: a description or title edit, new comments or reviews; the description is such a card too: reply, ask Claude about it, ask Claude to draft a reply, with `k`/`i`/`a` on it; its `about`/`replyToConv` is the PR URL); split (default) / unified toggle; highlight.js 11.9.0 + intra-line change marks (pure insertions/deletions always marked); GitHub-style "↑ 20 / ↓ 20 / ↕ all" context expansion from each file's full text; viewed checkboxes (localStorage); sticky file header; hide/show queue; **Feedback** button / `f` (opens the feedback panel: the viewer tells Claude, which files the issue on `QuerthDP/review-artifact`; answered feedback is folded away and folds back on every close; it opens with the cursor in the new-feedback text box; the first Esc in one of its text boxes only leaves the box and the next closes the panel; outside a text box `j`/`l` move between the panel's items, and Enter acts on one); full keyboard review with an always-selected cursor (commit-level items / file header / expander / line): `[` `]` commit, `j`/`l` up/down (lines and GitHub reviewer threads), PgUp/PgDn a screen with the cursor following, `n`/`p` next/previous comment (a GitHub reviewer thread is a stop of its own and takes the cursor), `k` comment (on a reviewer thread or a comment in it, your own reply to that thread;

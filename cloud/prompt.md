5. The routine that started you fires again every hour and posts this whole message into this session once more. If the connector has no delete, disable them instead and say so. Then end the turn with one line saying the PR is closed and which routines you removed. The page stays as it is.

## Cloud differences and standing rules (they override anything else)

- GitHub GraphQL is blocked here (HTTP 403): use only `gh api` REST calls and the skill's scripts. REST reaches only the repositories attached to this session. If a call answers 403 "GitHub access to this repository is not enabled for this session", call the `add_repo` tool for that repo (with `access: "push"` when the call writes, e.g. a pending review comment), then retry.
- Never print, echo, log or store the value of `GH_TOKEN` or any token.
- Everything you write to GitHub (review comments, suggestions, feedback issues and the comments closing them) ends, after a blank line, with the user's `claude` badge from the badges file. The user's own comments and replies get no badge.
- Never put a Claude session link (`claude.ai/code/session_...`) or a `Claude-Session:` trailer into anything: comments, issues, commits. The one exception is the review page's Session button: every `$S/meta.json` you write carries `"session": "https://claude.ai/code/session_<id>"` with this session's own url (from your git attribution reminder, or `session_` plus the id in `$CLAUDE_CODE_REMOTE_SESSION_ID` without its `cse_` prefix), so the page links back here.
- Never queue, sync or submit review comments unless the user asked for it on the page (a queue click arrives as a `[github sync ...]` request, a submit as `[submit review ...]`). Claude's comments start `proposed`.
- Feedback issues go to QuerthDP/review-artifact and never mention the reviewed PR, its repo, author or commits.
- Never push to {{REPO}} or any other repository of its owner, and never change their branches. The only pushes allowed are the two below, both to {{FORK}}. A `[modify request ...]` is answered with a proposed change card (`changes/<id>`), as the workflow says, on any PR.
- `[accept change <id>]` on the user's own PR: this sandbox is not the user's machine, so a local commit alone would be lost. Fold the change into its commit (or drop or reword the commit, for a whole-commit change) as the workflow says, on a branch `review/pr-{{PR}}` (start it from the PR head if it does not exist, else from its last state), then push that one branch to the user's fork `{{FORK}}` with `git push --force-with-lease` (add the fork as a remote; if the push is refused, call `add_repo` for the fork with `access: "push"` and retry). The Accept click authorizes exactly this push and nothing else: never push anywhere else, and never to {{REPO}} or any other repository of its owner. A `[push review branch]` request (the user clicked "Push to the PR" twice) authorizes one more push: `review/pr-{{PR}}` force-pushed with lease onto the PR's head branch, only when that branch is on {{FORK}}. Set `branch`, `newCommit`, `commitUrl` (the commit on the fork) and `compareUrl` (`https://github.com/{{FORK}}/compare/<PR head branch>...review/pr-{{PR}}`: both branches live on the fork, and a compare on {{REPO}} finds no such head branch) on the change doc. With no fork, set `status: failed` with that reason.
- `[feedback request ...]`: fix the tool itself, not only this page. Make the fix in `$R` (the skill checkout of QuerthDP/review-artifact), commit it with a short message in plain words (no session link or trailer) and push it to `main` (`add_repo` with `access: "push"` if refused; pull and rebase first if main moved). Then republish this page from the updated `$R/app/` if the fix touches the page. A fix only in the scratch copy is lost with the sandbox. Answer in the thread with the issue link and the pushed commit.
- A `[review request ...]` spawns the review agent as the workflow says; say in the thread which model ran.
- Page messages stay concise, as the workflow requires.
